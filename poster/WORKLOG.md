## 2026-09-07 · Claude (shune-aa) · 「六个方向」点了直接崩 —— 我自己写的，自检没接住

用户报："点六个方向直接卡bug了"。线上一点就复现：

`Uncaught TypeError: Cannot read properties of undefined (reading 'forEach')`

托盘开出来是空的。

### 根因

上一轮做「回到上一步能拿回当时那六张」时，我给 `showTray` 加了一个参数：

```js
function showTray(reuse){ const r = reuse || propose(6, TRAY_VARY); ... }
```

但按钮的绑定一直是：

```js
document.getElementById('topVariants').onclick = showTray;   // ← 事件对象被当成 reuse 传进去
```

于是 `r` 是一个 MouseEvent，`r.list` 是 undefined，`TRAY.forEach` 当场抛。

### 为什么自检没接住

**这一轮所有程序化用例调的都是 `showTray()` —— 永远不带参数。**
我测过递归、测过祖先条、测过三档切换、测过锁，全都是直接调函数，
唯独没有**点过那个按钮**。

这已经是这个项目里同一个坑的第二次了（上一次是键盘事件派发到 window 而不是 body）。
所以这次把结论写死在自检里：

> **新增用例「顶部按钮点下去真的出六个候选」，用 `dispatchEvent` 派发真实点击，
> 并挂 `window.onerror` 收集异常 —— 不是调函数。**

### 顺带解决「卡」的另一半

崩溃修好之后，线上点下去到画面变化仍有 **338ms 完全不动**。
`propose()` 加六张缩略图是同步的，这段时间浏览器没有机会画任何东西 ——
那也会被读成卡。

改成：点下去 **45ms** 托盘就出现（骨架屏 + 「现在这张」的大图 + 锁条），
候选放到下一帧再算；从「走过的路」端回来的那六张不用等，同步就有。

**一个真实存在的坑**：只挂 `requestAnimationFrame` 是不够的 ——
rAF 会被节流（后台标签页，或者这一帧本来就没有东西要画）。
实测递归那一步就这么空过一次，候选一直没填上。必须加 `setTimeout` 兜底。

而自检是**同步**跑完的，rAF 根本不会推进，所以那条用例要同步逼 `TRAY_FILL()` 算出来，
并且只数 `.cand:not(.cand-skel)` —— 否则量到的是六个骨架而不是六个候选。

### 同时压了一轮等待时间

| | 改前 | 改后 |
|---|---|---|
| 点击到候选出现（本地） | 315ms | 172ms |
| 点击到**托盘出现** | 315ms | **45ms** |
| `genState()` 一次 | 6.7ms | 约 3ms |

三处：
- `textMetrics` 加缓存 —— 落位一次要评几百个候选，每个都逐字 `measureText`，
  这是整条链上最贵的一步
- 候选池 30 → 16（最远点采样从 16 个里挑 6 个间距已经够，
  实测可分辨度反而从 1.47 **升到** 1.56）
- 沿对齐线滑动的步长 2U → 3U

### 自检 23 / 23

实测：托盘出现 45ms；递归连点五步每步都是 6 个；三档切换都对；
回上一步立刻拿回原来那六张；全过程 0 报错。线上复验同样通过。

### 三、间隙律（调研原话：比对齐更重要）

两块文字的纵向净间隙 g：

- `g ≤ 1.0×小cap` → 读作同一段（p-035 实测 0.5×cap、p-021 实测 0.8×cap）
- `1.0×小cap < g < 2.4×大cap` → **危险区，禁止**（44 张里没有一张落在这里）
- `g ≥ 2.4×大cap` → 读作两个独立构件（p-020 实测 2.4×cap、p-003 实测 3.2×cap）

> 对齐错了只是不整齐，间隙落在危险区是**直接读作错误**。

### 四、最小字号是墨/纸反差的函数，不是常数

`minCapPct(ΔL*) = 1.0 + 6.0·max(0,(35−ΔL*)/35)`，单位是画幅高的百分比。

三个校验点全部来自 p-031/p-032 —— 本轮唯一的**控制变量对照**（同一版式只换墨与纸）：

| ΔL* | 公式给的最小字高 | 实测 |
|---|---|---|
| 37.3 | 1.0%H | 1.1%H 可读 ✓ |
| 18.5 | 3.8%H | 7%H 可读 ✓ |
| 12.5 | 4.9%H | 1.1%H **消失**、11%H 仍可读 ✓ |

我们有 18 支墨 × 6 种纸 = 108 种组合。生成器守着 ΔL*≥30，
但用户手调颜色可以调到更低 —— 实测黄墨压米色纸 ΔL*=2.7 时，最小字高被抬到 6.5%H。

### 五、兜底解：给排不下的那行字铺一块自己的实地板

调研把这条排在"效果最大"：

> "完全压入"最保险的形式不是把字压进复杂图形，而是**先铺一块自己的实地**。
> 成本只有 4 个数字，效果等于重新构图。

实测出处：Cieslewicz p-019 板 35%W×16%H、Foroutan p-031 板 82%W×22%H、
Lenica p-011 带边框文字板占 7.7% 面积。

实现：板 = 文字 bbox + 0.6×cap 的 padding，用墨色实地，字挖成底色；
面积上限 20% 画幅（超了说明该缩字号而不是铺更大的板）；标题不铺板（它够大，
压在形上靠挖白就成立）。板必须画在**最上面且不透明** —— 它就是为了不受底下影响
才铺的，所以不能参与挖白那一遍（被裁进形里会变成半块矩形）。

**触发依据换过一次**：一开始按落位分数触发，铺板率 **27.4%**，太高而且依据是代理量。
改成直接量"这行字到底有没有压了一半在某个形上"（完全避开不用板，
整个压进去也不用 —— 挖白就成立），铺板率降到 **18.1%**。

出来的效果就是实测里数到 7/44 张的"独立信息带／报头"：展期与场馆压在一条实地带上。

**"文字看不见"这条指标一路的变化**（有文字 vs 无文字逐段比像素）：

| | 比例 |
|---|---|
| 起点 | 0.52% |
| 最小字号 + 间隙律 | 0.06% |
| 叠印补画 | 0.24%（样本不同，见上一条日志） |
| 铺板 | **0.05%**（1/1992） |

### 一、第一帧是空白画布 —— 这是最大的可玩性 bug

调研原话：

> 空白画布提出的问题是「你想做什么？」—— 这是用户答不出来的问题。
> 已完成的海报提出的问题是「你喜欢这张吗？」—— 这是任何人 0.5 秒就能答的问题。

它把看过的同类工具全列了一遍：studio-ity 结构上不可能空白（必须先带图进来）、
Infinite Craft 开局桌上就摆着水火风土、Hofmann 开局就是网格、Silk 一拖就出光、
Patatap 按任意键就有 —— **留得住人的，第一帧全都不是空的**。

更糟的是我们的展讯**本来就已经生成好了**，只是躺在右边栏里，要点三次「＋」才上画布。

改：启动时 `seedPoster()` = `newBrief() + shuffleState()`，展讯的两三行默认就在画布上。
空白态保留在「清空」后面，给知道自己要干嘛的人。

（原来那行注释写的是「启动时不再展示它，避免示例锚定用户」。实测推翻了它。
锚定的风险是真的，但**没有人留下来被锚定**才是更大的问题。）

### 二、托盘不读当前状态 —— 投入越多越不敢按

原来 `propose()` 里全部走 `genState()`，**完全不参考当前的 S**。
用户花三分钟做的东西，按一下按钮看到的是六张跟他无关的画。
调研管这叫「对已投入的惩罚」，也是用户不敢按第二次的原因。

而且选中一个候选托盘就关了 —— 选择是一个**终点**动作。
Artbreeder 的候选是**起点**动作：点一个 child，它立刻成为新的 parent 再生一窝。

改（调研把这条排在性价比第一）：

- 点候选**不关托盘**，把当前这张推进「走过的路」，从新的这张再出六个
- 托盘里常驻「现在这张」的大图 + 最多 8 张的祖先条，点回去就回去
- 固定留一格「远亲」（全随机、打红色角标）—— 连点几次之后六个会全长一样（局部最优），
  这一格是每轮保留的跳出机会。推荐系统里叫 ε-greedy，这里 ε = 1/6

### 三、「按一下该变多少」是量出来的，不是拍脑袋

调研在线上页面跑了 **600 个随机状态、179700 对两两配对**，加上单轴扰动标定：

| 带 | fdist | 参照系 |
|---|---|---|
| **死区** | < 0.25 | 元素横移 10% 画布 = 0.10，切线滑 10% = 0.14，放大 1.3 倍 = 0.18 |
| **抖一下** | 0.35–0.9 | 换字体 0.48、换重复档 0.50、换填充 0.67、换字号 0.67、加一个元素 0.70、换形 0.89 |
| **近亲** | 0.9–1.4 | 「还是同一张海报的另一个版本」 |
| 全新 | 中位 1.53 | 四分位 1.20–1.83 |

我上一轮只设了一个下限 0.42，结果近亲档的中位数是 0.96 —— **横跨在抖一下和近亲两条带之间**。
现在改成按带做拒绝采样，三档：

| | 目标带 | 实测（每档 40 个候选） |
|---|---|---|
| 抖一下 | 0.35–0.90 | 0.44 – **0.67** – 0.90 |
| 近亲 | 0.90–1.42 | 0.90 – **1.09** – 1.42 |
| 全新 | — | 0.85 – **1.69** – 2.58 |

**128 个候选里落在死区的：0 个。**

还照抄了调研里的一条 gotcha：`removeLastElement = 1.67` 是个**假高值** ——
元素删光之后 `feat()` 里的 e 退回默认对象，同时元素个数那一维直接掉 0.7，两处叠加，
空画面在特征空间里是一个孤立的极端点。所以变奏时禁止把元素数减到 0，
否则一次变奏看起来像重置。

### 四、这一轮抓到的三个真 bug

**1. 变奏会绕过用户手动上的锁。** 变奏为了制造差异会挑一两个维度重掷，
但那不能凌驾于锁之上。实测：锁了「色」，近亲档里 **7/36** 换了墨、抖一下档 **5/36**。
改成 `L[k] = (LOCKS[k] || 没被选中) ? 锁 : 放开`。
兜底那一支也传错了参数（`applyLocks(g, base, {})` 等于一个都不锁），一并修。
修完：三种模式 × 六个维度 × 六个候选 = **324 个，0 漏 0 没动**。

**2. 信息行出现两次。** 展讯的信息行既是底部固定的那行（`drawInfo`），
又能作为可拖的文字块加到画布上。以前要手点才会重复，现在默认三行都上画布，就必然撞。
改：画布上已经有 `brief:meta` 文字块时，`drawInfo` 不再印一遍。

**3. 文字落位发生在元素定好之前。** `shuffleState` 末尾只 `placeTitle()`，
正文和信息行是在中途排的 —— 它们躲的是**上一版**的形。
改成末尾统一 `placeAllTexts()`：标题先排（它最大，先占最好的位置），其余依次躲开。

### 五、还有两条是「排不下」而不是「没排好」

60 次随机、111 对文字两两组合，一开始有 **10 对重叠**。查下来两个原因：

**竖排正文 + 竖排标题 = 两根通天的列**，任何一行横排文字都必然横穿它们。这是无解的。
改：一张海报最多留一行竖排（标题竖排时，正文和信息行一律横排）。

**真的塞不下时应该缩小，不是硬塞。** `placeText` 现在发现最优解仍然撞字时，
把这一行按 0.78 / 0.60 缩小重排；标题不缩（它是画面的主音，宁可让别的让它）；
缩到 0.6 还不行就保留**最轻**的那一档，不盲目还原。

结果：**10/107 → 3/111**，两行竖排 0 次，140 个文字块里 25 个被自动缩过。

### 一、锁：把随机从赌博变成搜索

来源：**bauhaus.graphics**（Kurt Gehring）。官网原文一句话就是全部答案 ——
*"Lock settings you love and randomize the rest to explore endless visual possibilities."*

为什么这条重要：「全部重掷」的致命伤是**好不容易碰到一个喜欢的局部，一按随机就没了**，
于是人不敢按，随机按钮的使用率崩塌。加锁之后随机的期望收益永远为正
（喜欢的保住、不喜欢的换掉），按下去的心理成本归零。

更深一层：锁 k 个维度 = 把搜索空间从 D 维降到 D−k 维，用户实际是在做**坐标下降**。
那正好是人能感知因果的粒度 —— 全维随机时人什么也学不到，
锁到只剩一两维时人才开始理解「这个参数是干嘛的」。

六个可锁维度，正好对上状态 `S` 的天然分组：

| 锁 | 管什么 | 键 |
|---|---|---|
| 切 | 切线角度与位置 | `cut` |
| 色 | 纸、两支墨、浓淡 | `stock paper inkA covA inkB covB a b` |
| 形 | 有哪几个形、各是什么 | 每个元素的 `k cu` |
| 摆 | 在哪、多大、转多少、重复几次 | `x y s r rep` |
| 字 | 字体、字号、横竖、位置 | `texts` |
| 印 | 网目、纸纹、填充、套印 | `dot tex mis` + 每个元素的 `fill d3` |

**踩到的一处**：锁「摆」时元素个数还跟着新状态走，多出来的那个只能复制上一个的位置，
于是两个形精确重叠。改成**锁「形」或锁「摆」都把个数一起锁上**。

**实测**：8 轮 × 6 维 × 6 候选 = **288 次**，锁上的 **0 漏**，没锁的 **0 没动**。
六个全锁时，六个候选和原版完全一致。

### 二、近亲：全局重掷之外的第二档

来源：**INKDRUM**（Jackson Greathouse Fall）。它有两级随机：
`RANDOM RUN` 全局重掷 + `SHAKE` 局部微扰，而且 `SHAKE` 旁边紧挨着 `ALIGN` 归零 ——
**惊喜和撤销惊喜是相邻的两个按钮，所以人敢按**。

我们原来只有全局重掷。越接近满意，越不敢按。

实现上「近亲」和手动锁是**同一个机制**：除了一两个维度，其余全锁；
放开哪个由程序逐个候选轮着换，保证六个改的地方各不相同。

**一处必须加的下限**：低于 `fdist 0.42` 的候选直接丢掉 ——
改了一处但看不出来，等于白按。加之前近亲最近的那个只有 **0.39**，加之后 **0.55**。

**惊喜度实测**（fdist 到当前这版，12 轮平均）：

| | 最近 | 平均 | 最远 | 六个彼此可分辨 |
|---|---|---|---|---|
| 全新 | 1.13 | 1.69 | 2.17 | 1.51 |
| 近亲 | 0.55 | 0.96 | 1.47 | 0.95 |

出六个方案 **13.2ms**。

### 一、放大显示不全：从来没算过「这个形最大能放多少」

把手拖动只把尺寸卡在 `s ≤ 0.42`，那是个凭空的数：

- 觚的高宽比 **5.20**，`s=0.42` 就是 **1.09 个画布高**，必然被切掉半截
- 重复排 5 件的总宽是单件的 **11.4 倍**，`s=0.2` 就已经探出画面两倍宽

而 `clampEl` 只对器物做「缩小到放得下」，几何形完全不管（那是有意的：允许出血），
于是重复排的几何形一路长出画面。

`elBBox` 的 `ew`/`eh` 都是 `R0` 的**线性函数**，所以最大值可以直接解出来，不用迭代试：

> `ew = R0·(|cos r| + hf·|sin r| + |cos ra|·g)`，`hf` 是高宽比的一半，`g=(rep−1)/2·2.35`

新增 `maxElS(e)`：器物和自定义形要求整个在边距里；纯几何形允许出血，
但外接框半宽最多 **0.72 个画布**（再多就不是裁切，是没放下）。
把手拖动改成**先定角度再算上限**（能放多大取决于转成什么角度），拖到顶给一句人话提示。

**实测**：12 种形 × 3 档重复 × 3 个角度 = **108 组**。
旧版 **81 组超框**，新版 **0 组**。已写进自检。

### 二、填充点了没变化：立体开着时四个按钮全部失效

`drawOne` 里 `dots = three || ...`，`three` 一真就直接走 tone 通道，`fl` 根本没人读。
另外「半网」原本只在元素**跨切线**时成立（一侧实心一侧网点），
没跨线（或者压根没切）时退化成实心，和「实心」一模一样。

**A/B 实测**（同一个器物，逐像素比对整张画面的差异比例）：

| 场景 | 旧版 实心vs网点 | 旧版 实心vs半网 | 新版最小差异 |
|---|---|---|---|
| 无切线 · 平面 | 4.32% | **0.00%** | 2.52% |
| 无切线 · 立体 | **0.00%** | **0.00%** | 2.41% |
| 有切线未跨线 · 立体 | **0.00%** | **0.00%** | 2.41% |
| 有切线跨线 · 立体 | **0.00%** | **0.00%** | 2.36% |

24 组配对里旧版有 **13 组完全零差异**。现在全部不同，最小 2.36%。

改法不是把按钮禁用，而是让它们在立体下**换一套含义** —— 四种把三维明暗印出来的方式：

- **实心 → 色调分离**：明暗压成三级（0.10 / 0.46 / 0.88），像丝网印的分色版
- **网点 → 连续调**：网点大小跟着明暗走（原来的样子）
- **渐变 → 上浓下淡**：明暗再乘 `(1.15 − 0.95·g)`，形往下化开
- **半网 → 只印暗面**：`a < 0.42` 直接不落墨，亮面留成白纸

平面下的「半网」没跨线时改成**沿元素自己的中线上下分半**（上网点下实心），手法不变，永远看得见。

### 三、文字落位：不是「找空地」，是「只准落在对齐线上」

旧版 `placeText` 只有**四个角**四个候选，评分只看重叠面积，平手就按顺序取第一个。
实测「两个形偏左」那一组：**两行字落在完全相同的坐标 (33,33)**，重叠 1295px²。

新版：

1. `layoutLines()` 立**对齐线**：两条页边距永远保留，每件形的四条边各自参选，
   相距小于 3U 的合成一条，**每个方向最多三条**（线一多就等于没有线）
2. 每条竖线可以当左边界也可以当右边界，横线同理 → 候选点
3. **跟排**：直接接在已有某一行后面，共用它的对齐线（海报里最常见也最好看的关系）
4. **沿对齐线滑动**：只用四个角是不够的，画面一挤四个角全被占，它就只能压到形上去。
   贴住同一条线上下（或左右）滑，对齐关系保住，位置让开
5. 评分：撞到别的字 **1e6 一票否决**（上一版给 4000，和「躲开三个网点形」同量级，
   结果它宁可把副标题压在标题上 —— 截图抓到的）；
   和形的关系罚的是**压一半**不是「压」（整行落进一块够大的实地墨里，形会把字挖成底色，
   那是双色印刷最漂亮的一手；压一半才是一行字从中间断成两个颜色）；
   共用一条对齐线 −140；竖排中文从右上起排、横排从左上起（读的方向，不是审美偏好）；
   重心别跑偏

**实测**（5 种画面 × 4 行字）：

| | 文字互压 px² | 压一半的行数 |
|---|---|---|
| 旧版 | 35 / **1295** / 35 | — |
| 新版 | **0 / 0 / 0 / 0 / 0** | **0** |

单次落位 **0.57ms**（不在每帧路径上，只在加文字和换展览时跑）。

**还没解决的一处**：画面被一个 `s=0.40` 的大形吃掉大半、同时要放四行字时，
确实找不到干净的槽位，会有一行落在网点形上。那是画面真的满了，不是算法选错。

## 2026-09-07 · Claude (shune-aa) · 真三维明暗（推翻上一版的分层错位）

用户："立体效果很差，我想要真实的立体效果类似于3d，效果就像是风格化的三维建模渲染一样。"

**上一版做错了方向。** 分层错位（layered offset）是平面印刷的把戏，不是三维 ——
它只是把同一个剪影错开几层，没有任何光照、法线或体积。我当时按调研里
"双色语言里最不违和"的建议选了它，但用户要的是**真的三维渲染**，那条建议答非所问。

**这一版的做法**：

> 把 3D 渲染出来的明暗当作"墨的覆盖率地图"，再交给已有的半调网屏去印。

关键不是"贴一张 3D 图上去"，而是**用两支墨把三维印出来**：
- 光照、法线、边缘光、环境光遮蔽、一点点高光，全都是真算的（`shadeAt()`）
- 器物走**旋成体的圆柱面明暗**：每一圈在正交投影下是一条水平线，
  线上每点的法线由它在圆周上的角度决定；母线的斜率给出纵向法线分量
- 圆和环走**球面**：从 (x,y) 反解 nz，标准 lambert
- 其余走沿光源方向的柱面近似
- 输出是一张灰度图 = "这里该有多少墨"，`screenFill` 新增 tone 通道，
  按该处明暗决定每个网点的大小

这样它既是真三维渲染，又仍然是双色印刷 —— 而且天然守住原有的全部约束：
网屏仍锚在纸坐标系、覆盖率仍走 `inkR` 的可印区间、跨切线仍然反色。
丝网印和 riso 印立体物本来就是这么印的。

**性能**：明暗图按元素特征缓存（`toneCache`，上限 16 张）。
但带 tone 的网点循环不能复用整张网屏缓存（每个点大小都不同），所以
**拖动时降质**：`drag` 为真时三维元素画实色，松手再补网点。
实测拖动 **0.33ms**、静止 **7.33ms**，自检 **15/15，最坏帧 3.63ms**。

**顺手删掉**：`e.dep` 分层错位的整段渲染代码与四档控件，换成 `e.d3` 平面/立体。
